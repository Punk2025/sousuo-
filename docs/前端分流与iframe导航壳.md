# 前端分流 + 全屏 iframe「导航壳」逻辑说明

> 研究笔记：对照公开站点观察到的行为做拆解。  
> 用途：理解手法、做识别/打标。**不是实现教程。**

---

## 1. 一句话

同一 URL 上叠两层东西：

1. **内容壳**：给搜索引擎看的「情感社区」静态页（SEO）  
2. **导航壳**：给普通浏览器用户看的全屏加载页 → 再嵌外站页面  

对人、对爬虫展示不同结果，所以叫「分流」。

---

## 2. 谁在什么时候触发

页面会挂一个业务脚本（示例站里类似 `o1b730.js`），大致逻辑是：

```text
打开页面
  → 读 User-Agent
  → 像爬虫/自动化？（spider、bot、curl、headless…）
        ├─ 是 → 不跑跳转逻辑，只留 SEO 内容页
        └─ 否 → 执行「导航壳」初始化
```

目的：尽量让百度/Google 抓到「干净内容」，真人却进外链层。

（有的变种还会看 Referer 是否来自搜索引擎；示例脚本里相关判断被注释掉了，当前主要靠 UA。）

---

## 3. 真人侧实际流程

```text
1. 注入全屏 Loading UI
   文案类似：「正在为您寻找最佳连接路径」

2. 动态插入一个全屏 iframe（盖住整站，z-index 极高）

3. 拉取远程配置
   - 地址常在第三方（如 npm 镜像上的某个包 latest）
   - 返回里有一段密文 data

4. 本地用密钥解密（常配合 crypto-js 一类库）
   - 得到 JSON，其中通常有 index（要打开的落地地址）

5. 给落地 URL 拼渠道参数（如 c=xxxx）

6. iframe.src = 落地地址
   - 加载成功后隐藏 Loading
   - 用户看到的是外站「导航/落地」页，不再是情感社区正文
```

视觉上：短暂转圈 → 整页变成另一个站。地址栏往往还显示原域名，所以有「还在原站」的错觉。

---

## 4. 角色分工

| 部件 | 作用 |
|------|------|
| SEO HTML | 关键词、栏目、JSON-LD、sitemap，喂收录 |
| 统计脚本 | 百度统计 / CNZZ 等，看流量 |
| 分流脚本 | 判访客、拉配置、开 iframe |
| 加密配置 | 落地地址可远程改，不用改站点文件 |
| 渠道参数 | 统计从哪个壳站/哪条线过来 |
| 外站 H 页 | 真正的「导航」或后续导流页 |

内容站本身可以几乎是静态文件；「跳到哪」由远程配置决定。

---

## 5. 和真论坛 / 普通导航页的差别

| | 普通站点地图 | 这种「导航壳」 |
|--|--------------|----------------|
| 链接 | 指向本站栏目 | 指向外域落地 |
| 展示 | 人人一样 | 爬虫与真人可能不同 |
| 技术 | `<a href="/intro/">` | UA 判断 + 解密 + 全屏 iframe |
| 地址栏 | 会变到子路径 | 常仍停在原域名 |

---

## 6. 识别特征（给打标 / 人工复核）

静态或抓源码时可看：

1. 同时存在「长文 SEO 页」+ 可疑短脚本（含 spider/bot 判断）  
2. 引用 `crypto-js` 或自写加解密，却几乎无支付/登录需求  
3. 运行时出现全屏 `#contentFrame` / `loading-container` 一类节点  
4. iframe 指向无关外域，且带短渠道参数 `c=` / `channel=`  
5. 请求第三方「配置包」latest / 加密 `data` 字段  
6. meta generator 像自研 Publisher，但交互能力（发帖登录）缺失  

SearchPipe 侧可记标签示意：`疑似前端分流` / `iframe导航壳`（规则需结合脚本特征与外域 iframe，避免误伤正常埋点）。

---

## 7. 设计上为什么这样拼

- **收录**：壳站好做关键词、栏目、结构化数据  
- **可控**：落地 URL 在远程配置里改，批量换线方便  
- **隐蔽**：地址栏仍是壳域名；爬虫少看到外链层  
- **成本**：静态托管 + 一个 JS，比真论坛便宜  

对应风险也高：搜索违规、用户欺诈感知、域名/备案被打等——研究识别即可，不要当业务方案。
